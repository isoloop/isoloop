# 0.1.1: the first patch

**Goal:** `0.1.1` on npm as `latest`, released from `release/0.1`, with the fixes from the external 0.1.0 audit (2026-11-24) that fit a patch. Everything else is filed for 0.2.

**Done when:** `0.1.1` is published with provenance from `release/0.1`, every task below is closed, and the web repo has the 0.1.1 pin (its own plan).

**Progress:** the tracking issue (linked from this plan's PR) has one sub-issue per task. A PR closes its task with `Fixes #N`. Backports tick the box in the task's issue. This file holds no checkboxes.

## Decisions (2026-11-24, grilled Q1–Q18, maintainer, yes to all)

1. **Branches.** `main` moves on to `0.2.0-next`. `release/0.1` is cut from `v0.1.0` (ADR 0019, decision 5). Every fix merges to `main` first with a patch changeset, then goes to `release/0.1` as its own PR. The guide, API page and diagram fixes go back as one combined PR. `main` stays at `0.1.1-next.N` with no `next` publish until the first 0.2 change brings a minor changeset.
2. **The branch stays after 0.1.1,** for a 0.1.2 if one is needed. It's deleted when `0.2.0` is `latest`, and its tags stay.
3. **Releasing from the branch.** `release.yml` and `scripts/release/rules.ts` admit `release/0.1` by its exact name, never `release/*`. The maintainer adds it to the `npm` environment's branch policy and gives it a ruleset like `main`'s. A dry run on the branch comes before the real stage. The tag comes on the maintainer's word.
4. **The site pin.** The web repo's `build/pin.ts` only accepts a commit reachable from `main`. It has to accept `release/0.N` as well. That change goes in the web plan's pin-bump task.
5. **#390, the slow crash loop, gets an internal rule now.**
   - A crash counts toward `maxRestarts` when the healthy run before it was shorter than `withinMs`. A run of `withinMs` or longer clears the count. The sliding window stays as well.
   - The healthy run lasts from `ready` to the last heartbeat, not to the kill.
   - The bus worker uses the same rule.
   - The types don't change. An explicit `healthyAfterMs` option is 0.2.
6. **#389, the starved Firefox worker: docs only in 0.1.1.** The supervision guide states the limit with the measurements, plus one more: the same starvation at the default `killAfterMs`. The design gets its own grill and ADR for 0.2.
7. **#389 and #390 interact.** In #389's runs, starved pages recovered only because the window let them. Before #390's code merges, #389's starvation setup runs on the new rule, at the defaults and at `killAfterMs: 2000`. If pages reach `failed` at the defaults, the rule waits for 0.2 and 0.1.1 ships without it.
8. **#346, the balancer: no API change in a patch.** The guide states that a new isolate shows as `quarantined` and leaves with `steady` while it's measured, and that passing `loads` avoids it. `measuring` and `measured` are 0.2.
9. **`useTopic` twice on one topic: a warning now.** With the kernel's `dev: true`, a second `useTopic` mounted while the first still is warns once per topic per isolate (React, Preact, and `useRoute` through it). Behaviour doesn't change. The fan-out is 0.2.
10. **ADRs: no new ones.** ADR 0001 and ADR 0007 are amended for decision 5. ADR 0010 is amended because the host applies `style` records through the CSSOM (#357): the protocol is unchanged, and a page runs under `style-src 'self'`. Both amendments go to the maintainer before their code. ADR 0019's status line records that the branch path is built.
11. **Agents.** Each task runs in its own worktree and its PR merges itself on green CI. The exception is T5's and T6's ADR text, which goes to the maintainer first. T3 leaves the supervision guide's restart-window text to T6.
